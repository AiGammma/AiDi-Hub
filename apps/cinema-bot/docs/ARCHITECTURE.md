# Архитектура

## Слои

```
bot/handlers.py            Telegram: разбор ввода, вызов сервисов, форматирование
        │
services/                  вся бизнес-логика, не знает про Telegram
  recommender  profile  importer  directors  catalog  users
  taste  english           чистые функции (вкус, «полезность для английского»)
  entitlements  payments   тарифы, квоты, подписки        ← монетизация
  privacy  export          согласия, удаление, выгрузка    ← данные
        │
domain/ports.py            интерфейсы: MetadataProvider, Explainer, PaymentProvider
        │
adapters/                  tmdb · kinopoisk_csv · claude   (заменяемые)
db/models.py               схема SQLAlchemy (SQLite сейчас, Postgres потом)
app.py                     единственное место, где выбираются реализации
```

Правило: сервисы зависят от портов, а не от TMDB, Claude или Telegram. Заменить каталог, LLM или платёжную систему можно, не трогая логику.

## Как строится подборка

1. **Кандидаты:** вишлист + фильмография любимых режиссёров + «похожие» (TMDB) для того, что ты оценила на 8+. Просмотренное, отклонённое и показанное за последние 45 дней исключается.
2. **Оценка:** профиль вкуса (веса жанров, режиссёров, ключевых слов, актёров, десятилетий, стран) считается из оценок относительно твоей средней. Плюс бонусы за источник и небольшая поправка на рейтинг TMDB.
3. **Режим `/english`:** жёсткий фильтр «оригинал английский и производство США», затем мягкая оценка (современная разговорная речь, комедия/драма, сериалы с короткими сериями — плюс; исторические, фэнтези, военные, вестерны, британские и прочие акценты — минус).
4. **LLM-реранк (необязателен):** Claude выбирает финальные 5 из шортлиста, пишет персональное объяснение и (в `/english`) словарь жанра. Любой сбой, отказ или невалидный JSON → откат к правилам, бот от LLM не зависит.

## Модель данных и почему она готова к росту

* Всё личное привязано к `users.id`. Многопользовательность не надстройка, а исходное условие.
* `titles`, общий каталог без персональных данных; личное в `user_titles`, производное в `taste_profiles`.
* `users.public_id` единственный идентификатор, который вообще может выйти за пределы системы (и то только перемешанным солью).
* `consents`: согласия по целям, по умолчанию всё выключено.
* `usage_events` пишутся всегда, даже при выключенной монетизации, чтобы цены и лимиты выбирались по реальному поведению.
* `payments` переживают удаление аккаунта (связь с пользователем обнуляется), остальные личные данные удаляются полностью.
* `export_log`: аудит каждой выгрузки.

## Монетизация: что уже есть и как включить

Есть: тарифы и квоты (`services/entitlements.py`), учёт использования, подписки, идемпотентная активация по вебхуку (`services/payments.py`), порт `PaymentProvider`. Хендлеры бота уже проходят через `check` → действие → `record`.

Включить:

1. Реализовать `PaymentProvider` (проще всего Telegram Stars для цифровых товаров внутри Telegram; для карт — ЮKassa или Stripe через вебхук) и подставить в `app.py` вместо `NullPaymentProvider`.
2. В обработчике оплаты вызвать `SubscriptionService.activate(PaymentEvent(...))`.
3. Добавить в `/plan` кнопку покупки.
4. Подобрать числа в `PLANS` по `usage_events`.
5. `CINEBOT_MONETIZATION_ENABLED=true`. Свой Telegram id в `CINEBOT_OWNER_TELEGRAM_IDS`, чтобы не упереться в лимиты самой.

Новая платная функция = константа в `entitlements.py` + строка в `PLANS` + `check/record` в хендлере.

## Выгрузка вкусов: что уже есть и какие там границы

CLI: `python -m cinebot.cli export aggregate|vectors --requested-by "<кому>"`.

* В выгрузку попадают только пользователи с согласием `data_export`, не удалённые и с минимумом оценок (`CINEBOT_EXPORT_MIN_RATINGS`).
* Идентификаторы псевдонимизируются HMAC с секретной солью (`CINEBOT_EXPORT_SALT`, без неё выгрузка не работает). Поменяешь соль, и наборы нельзя будет склеить.
* `aggregate` (по умолчанию): статистика по фильмам, скрытая, если оценок меньше `CINEBOT_EXPORT_MIN_GROUP_SIZE` пользователей.
* `vectors`: веса жанров, десятилетий, стран, языка, без имён режиссёров и актёров и без оценок по отдельным фильмам. `--include-ratings` добавляет оценки по фильмам; по набору из нескольких оценок человека можно узнать, так что отдавай такое только по договору с получателем.

### Что нужно сделать до первого реального пользователя и тем более до продажи данных

Это не юридическая консультация, это список вопросов к юристу.

* Политика конфиденциальности и текст согласия. Сейчас в `/privacy` короткие формулировки-заготовки; при их смене увеличь `POLICY_VERSION`.
* Если пользователи из РФ: локализация персональных данных (152-ФЗ) и уведомление Роскомнадзора. Из ЕС: GDPR. Передача данных партнёрам требует отдельного явного согласия. Оно есть технически, юридически его формулировка за тобой.
* Условия использования Кинопоиска и TMDB (TMDB отдельно ограничивает коммерческое использование API, нужна их коммерческая лицензия).
* Оценки и вишлист из Кинопоиска это данные пользователя, а не Кинопоиска, но пользователь загружает их сам, и это стоит прописать в условиях.

## Что сознательно не сделано

* **Миграции.** Сейчас `create_all`. Перед первыми реальными пользователями и переездом на Postgres подключить Alembic.
* **FSM в памяти** (`MemoryStorage`): после перезапуска бот забывает, что ждал файл. Для нескольких инстансов заменить на Redis.
* **Фоновые задачи.** Импорт идёт прямо в хендлере. Для сотен пользователей вынести в очередь.
* **Векторы смысла.** Вкус считается по признакам; эмбеддинги описаний можно подключить за теми же `build_profile` и `score`, когда накопится данных.
* **Webhook-режим Telegram** вместо long polling и сам деплой.
* **Оценки внутри бота** (👍 пока не превращается в числовую оценку для профиля).
